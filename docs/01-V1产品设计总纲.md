# AI 客户作战系统 V1 产品设计总纲

> 状态：业务方向基本确认，细节持续评审
>
> 更新日期：2026-08-31
>
> 阅读方式：日常对齐优先阅读本文；表结构见[业务数据模型](02-业务数据模型.md)。原型盘点、通知研究和过程记录均作为内部附录保留。

## 1. 一句话定义

这是一套独立运行的 AI 客户作战系统：把销售跟进转成经过确认、可追溯的经营事实，持续更新商机阶段、客户作战位置和下一步动作，并通过地图、问数、周报与提醒帮助销售和管理者推进经营。

它不是通用 CRM，也不是把飞书多维表格原样搬到 Web。

## 2. 已确认的产品原则

1. Web 是正式入口，独立数据库是正式数据源；
2. 飞书只作为可插拔的通知和辅助聊天渠道；
3. Agent 不直接读写数据库，只能调用受权限和审计约束的业务 Tool；
4. Agent 框架、模型厂商、通知渠道和客户端都可替换；
5. 当前状态、历史版本、来源证据和查询投影分开管理；
6. Prompt、模型、阶段、象限、提醒和通知规则需要版本化；
7. 权限、审计和管理后台可分步建设，但底层接口与记录首期必须存在；
8. 飞书 DEMO 表结构只证明业务效果，不作为正式表结构；
9. 专业销售管理表只提供领域关系与经营任务参考，不把完整 CRM 范围带入 V1；
10. 首期可以用于演示，但按可试用、可演进的正式产品建设。

## 3. 经营对象边界

“经营对象”是可被持续经营、评估和安排动作的外部组织。V1 按统一模型支持不同类型，例如：

- 最终客户；
- 渠道；
- 伙伴；
- 厂商；
- 后续通过配置增加的其他组织类型。

客户、渠道、伙伴等共享负责人、联系人、商机、跟进、作战状态和经营动作，但可在规则和页面上有不同策略。公司内部团队和外部经营对象必须使用两套独立模型，避免把“销售组织”和“客户组织”混为一谈。

## 4. V1 业务范围

### 4.1 核心经营闭环

- 自然语言录入销售跟进；
- AI 识别经营对象、联系人、商机、事实、阶段和下一步动作；
- 生成结构化草稿，允许修改、确认或取消；
- 确认后写入正式经营事实和跟进记录；
- 更新商机阶段和客户作战状态，并生成待确认的建议动作；
- 销售或授权人员再次确认建议动作后，才形成正式经营动作；
- 更新销售工作台、作战地图和管理总览；
- 通过站内信及飞书发送销售结果和关键变化通知。

### 4.2 持续经营管理

- 管理者主动询问某位销售或团队本周进展；
- 生成个人周报和团队周报；
- 动作在提前、到期、逾期等节点提醒责任人；
- 关键风险或长期逾期按规则升级给管理者；
- 飞书卡片展示摘要并跳转独立 Web；
- 可选飞书聊天机器人转发到同一 Agent 接口，不保存独立业务逻辑。

### 4.3 暂不进入 V1 核心

- 完整线索、报价、合同、订单、回款和市场活动；
- 完整小程序客户端；
- 通用低代码工作流或 Base 表格编辑器；
- 任意 SQL 式自然语言 BI；
- 飞书与独立系统长期双主写入；
- 完整复杂组织和字段级权限管理后台。

## 5. 角色与工作台

### 销售

围绕“录入、确认、推进”组织：

- AI 跟进输入；
- 待确认草稿；
- 我的经营对象与主商机；
- 待办、逾期和信息缺口；
- 个人周报；
- 与本人相关的通知。

### 管理者

围绕“地图、变化、介入”组织：

- 客户作战地图；
- 关键上升、下降、停滞和风险；
- 团队商机阶段与动作完成情况；
- 主动问销售或团队进展；
- 团队周报；
- 需要管理介入的动作。

### 管理员/运营

首期只提供最小受控入口：

- 用户、团队与飞书账号绑定；
- 规则、Prompt 和模型版本查看与发布；
- Agent、通知和导入失败查询与重试；
- 审计记录查询。

## 6. 五条关键业务旅程

### 6.1 销售提交跟进

```text
原始输入
  → Agent 通过只读 Tool 补充上下文
  → 结构化草稿与对象匹配候选
  → 销售确认或修改
  → 业务模块校验权限、版本和幂等
  → 正式事实、跟进和阶段，并生成建议动作
  → 用户单独确认建议动作后形成正式经营动作
  → 新作战状态版本
  → 站内及飞书通知
```

未确认草稿不得进入正式数据；建议动作未经二次确认不得进入待办和提醒；通知失败不得回滚业务提交。

### 6.2 管理者查看作战地图

管理者先看 T0、关键变化、逾期动作和数据缺口，再看全量二维分布。每个点位都必须回答：为什么在这里、最近发生了什么、下一步由谁推进。

### 6.3 管理者主动问进展

系统解析人员、团队、周期和问题类型，通过有权限的查询 Tool 返回摘要、重点对象、阶段变化、动作完成/逾期和数据缺口。关键结论必须附证据，不允许对数据空缺进行合理化编造。

### 6.4 个人与团队周报

周报需要记录统计区间、数据截止时间、规则版本、发布状态和证据。个人周报突出本人完成、变化、下周计划和需协助事项；团队周报突出总体变化、重复问题、重点风险和管理介入，不是个人报告的简单拼接。

### 6.5 动作提醒

Agent 或规则先生成建议动作，销售或授权人员确认后才成为正式经营动作。正式动作包含责任人、计划时间、优先级、状态和来源。已发布提醒规则决定提前、到期、逾期和升级节点；完成、取消或改期后同步调整提醒计划，并防止多渠道重复轰炸。

## 7. 飞书现状：保留什么、重做什么

### 已经真实验证，应保留业务效果

- 自然语言跟进及结构化候选；
- 人工确认后正式入库；
- 六级商机阶段和阶段进度；
- 跟进成功后的销售通知；
- 关键变化时的管理者通知；
- 通知卡片中的客观事实、阶段、下一步和地图深链；
- 四象限地图、T0 独立区域、筛选和经营动作列表。

### 已出现概念但尚未跑通，需要重新完成

- 经营信号记录；
- 作战评估历史；
- 动作与来源评估的证据关联；
- 可版本化的关键变化条件；
- 完整授权、失败恢复和审计体验。

### 不照搬

- Base DEMO 字段和表间结构；
- 60/60 临时阈值与临时象限名称；
- 飞书 iframe 地图；
- 机器人长消息的高密度展示；
- 为个人单独复制的大量视图；
- 混合业务事实、公式、通知状态和页面投影的宽表。

## 8. 架构护栏

### 8.1 模块化单体优先

首期按客户经营、商机、跟进确认、作战分析、经营动作、报告、通知、身份权限、Agent 运行和配置审计划分模块，但保持单体部署。只有真实出现独立扩缩容或团队自治需求时才拆服务。

### 8.2 Agent 与 Tool

Agent 只负责理解、规划和提出候选；Tool 提供查询经营上下文、创建草稿、请求分析等业务语义能力；正式写入由确定性应用服务完成。任何模型都不能获得任意 SQL 或通用记录修改权限。

### 8.3 通知

站内通知是事实源，飞书和邮件是异步投递 adapter。生产飞书接入采用自建应用机器人与官方接口；CLI 只用于调试或 Tool，不作为通知服务运行时。

### 8.4 数据

关系型数据库承载正式业务数据；关键关联和查询字段结构化存储，实验性字段才进入受约束扩展结构。业务更正通过新版本表达，不能无痕覆盖历史。

## 9. V1 分段交付建议

> 工程仓库中的“V1-A 数据与身份基础”“V1-B 跟进确认”是纵向实施增量编号，不等同于下方产品范围的 V1-A/V1-B。产品范围仍以下方两段为准，避免把一个工程切片误称为产品 V1-A 已全部完成。

### 9.0 当前工程实现边界（2026-08-31）

已实现并可本地验收：租户/身份与经营主数据物理基础、经营对象目录、来源与草稿修订、人工确认/取消、正式跟进与事实证据、可回放作战分析、状态版本与当前地图投影、证据解释、建议动作独立接受/拒绝、正式经营动作状态机，以及审计/领域事件/Outbox 原子写入。正式动作接受后由独立 Worker 消费 Outbox，按不可变已发布策略生成到期提醒；到期后原子形成站内通知与投递记录，支持未读筛选、已读回执、业务深链、租约恢复、重试、死信和租户内去重。可选飞书 adapter 使用官方 SDK 发送摘要卡片，未配置或发送失败不会影响站内信和业务状态。

桌面与 390px Web 已覆盖销售/管理首页、跟进确认、原生作战地图、建议决策、正式动作流转和通知中心；AI 候选在人工确认前不会形成正式跟进或动作，重试使用稳定幂等键。首页按当前有效责任关系生成同一份严格快照：负责人/协作人可对责任对象的建议做决策，但只看和流转本人动作；管理观察者只读观察对象的建议与开放动作。建议、动作与地图深链在落地页及写事务中重复授权，无权与不存在统一按 404 处理。当前已完成“首页 → 事实 → 分析 → 地图 → 建议确认 → 正式动作 → 到期提醒 → 站内通知”的核心纵向闭环。尚未实现：管理问数、个人/团队周报、提醒提前/逾期/升级的正式业务参数、配置管理台、历史导入、生产 OIDC、真实租户飞书凭据验收和部署恢复验收。因此这仍不是完整产品 V1-A，更不是整个 V1。

### V1-A：核心经营闭环

- 跟进草稿与确认；
- 正式事实和商机阶段；
- 作战状态版本与原生 Web 地图；
- 建议动作确认、正式经营动作和基础提醒；
- 销售/管理首页；
- 站内与飞书摘要通知。

### V1-B：持续经营管理

- 管理问数；
- 个人与团队周报；
- 提醒升级与汇总；
- 可选飞书聊天 adapter；
- 首批历史数据迁移工具。

两个增量共用同一领域模型、接口、权限和审计，不分别建设统计逻辑。

## 10. V1 验收底线

- 未确认草稿不会改变正式业务状态；
- 重复提交只产生一次正式结果；
- 阶段、象限和动作均能追溯到事实、规则和分析版本；
- 管理问数只返回授权范围内的数据并带证据；
- 周报有稳定统计口径和不可变发布版本；
- 未确认建议动作不会触发提醒；正式动作提醒可去重、改期、停止、重试和升级；
- 飞书不可用时，Web、站内通知和核心业务仍正常运行；
- 更换模型/Agent adapter 不改变业务写入路径；
- 新客户端不复制领域规则。

## 11. 当前待确认事项

1. 个人周报是否由销售审阅后发布，团队周报是否由管理者审阅；
2. 周报周期、截止时间、推送时间和接收范围；
3. 动作提醒提前量、逾期频率和升级对象；
4. 关键经营变化的正式口径与降噪门槛；
5. 飞书聊天机器人只做管理问数，还是也允许辅助提交销售跟进；
6. V1 试点人数、数据量、部署可用性和预算；
7. 数据结构已确认保留 `tenant_id`；最终是单企业部署、集团多组织还是多租户产品仍待后续确定。
